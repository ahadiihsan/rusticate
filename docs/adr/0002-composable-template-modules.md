# 0002. Compose generated projects from optional template modules

- **Status:** Accepted
- **Date:** 2026-10-15
- **Deciders:** Platform team
- **Rules affected:** ARCH-* (tiers stay; which crates exist becomes a choice), ADR 0001 decision 2 (amended)

## Context

The template is one fixed stack: HTTP API, PostgreSQL with row-level security, NATS messaging with a worker, and the `billing` example. Every generated project gets all of it.

- Many backends need none of messaging, multi-tenancy or even a database on day one. They still pay for them: concepts to learn, 405 crates to compile, a worker to deploy.
- The example is product code the consumer must delete before building their own.
- The skills point agents at the example (`issue_invoice.rs`) for the shape of a feature, so they cannot work without it.

The crate graph already separates cleanly:

| Module | Owns | Requires |
|---|---|---|
| core | `apps/api`, `api-kit`, `server-kit`, `telemetry`, `op-context`, `iam`, `xtask`, harness | — |
| postgres | `datastore`, `idempotency`, `test-kit`, migrations, query metadata, the compose Postgres service, `db` commands | — |
| messaging | `messaging`, `apps/worker`, the compose NATS service | postgres (outbox and inbox are tables) |
| example | `billing`, `billing-engine` | postgres, messaging |

Two edges cross module lines and are cut: `server-kit → datastore` (readiness: the `ReadinessCheck` trait moves to `api-kit`, and `datastore` implements it) and test contexts living in `test-kit` (they move to `op_context::testing`, so tests without a database can use them). `apps/api → datastore` is wiring, marked with blocks.

## Decision

1. **The template stays the complete superset.** It always builds and passes `verify` with every module, so the full stack keeps being tested and documented in one place.
2. **The generator composes projects from modules.** A module owns whole paths, and marked blocks in shared files:
   - Markers are lines `rusticate:module(<name>):start` / `rusticate:module(<name>):end` inside the file's comment syntax (`<!-- -->`, `//`, `#`, `--`). Like template-only blocks, they must sit on their own lines and pair up; the generator rejects anything else.
   - A dropped module's paths and blocks are removed; a kept module's marker lines are removed, so generated code carries no markers.
   - `absent_paths` are stand-ins that exist only *without* a module (the core-only scaffold templates), removed when it is included. `template_only` paths (the generator's own CI checks) never ship.
   - Requirements are checked: `messaging` without `postgres` is refused.
   - A Rust file that lost lines is formatted with `rustfmt`; `cargo rusticate setup` formats again in case rustfmt was unavailable.
3. **Choosing modules.** `cargo rusticate new` asks one yes/no question per module in a terminal (default yes; a module whose requirement was declined is skipped). Flags answer without asking, for scripts and CI: `--minimal` (core only), `--with <modules>`, `--without <modules>` (also drops what needs them), `--bare` (`--without example`), `--all`. Without a terminal and without flags, the full stack is generated, matching earlier releases.
4. **Derived files follow their sources.**
   - Query metadata (`.sqlx/`) lives in each crate that has queries; sqlx reads it before a workspace-level one, so it leaves with its crate. sqlx-cli can only generate it for the whole workspace, so `db prepare` generates it there and gives each file to the crate whose source holds that query (same SHA-256 of the SQL text sqlx uses); a file no crate claims is an error.
   - `apps/api/openapi.json` is regenerated by `cargo rusticate setup` when it does not match the code, so a project with fewer modules starts with its own contract.
   - Documents link to code as evidence (the SOP cites the example and the platform crates). A relative link whose target left with a module is pointed at that file in the template repository, at the version the project was generated from, so it keeps working.
5. **xtask adapts at run time.** Scaffolding detects the modules from the crates present (`datastore`, `messaging`) and reads its templates from disk, choosing `xtask/templates/core/` without a database; the ARCH-004 rule that every feature has a `db.rs` applies only with one. Commands that exist only with a module (`db …`) are marked blocks.
6. **Skills do not depend on the example** (amends ADR 0001 decision 2). The canonical shape of a feature, domain or migration is what `cargo rusticate new feature|domain|migration` scaffolds; skills reference those scaffolds and state the remaining rules in their own words. The example is a deeper, optional illustration: documents mention it only inside `example` blocks, and module-specific guidance sits in that module's blocks.
7. **CI generates and verifies every supported combination** (smoke test): core only, core + postgres, everything without the example, everything. Each regenerates its contract and runs `verify --fast`; the core project also runs its tests and builds freshly scaffolded features.
8. **Multi-tenancy stays part of `postgres` for now.** A single-tenant PostgreSQL flavour (no row-level security, plain transactions) is a separate decision.

## Alternatives considered

| Option | Pros | Cons | Why not |
|---|---|---|---|
| Cargo features for optional parts | One codebase, toggled at build time | Code, dependencies and concepts stay in the project; every combination is a `cfg` maze | The consumer still owns code they did not ask for |
| Separate templates per stack | Simple generator | Shared code duplicated across templates; fixes drift | Maintenance cost grows with every combination |
| Remove the example from the template | Smaller template | Platform crates lose their end-to-end consumer and tests; agents lose a worked example | The example is the template's own test bed |

## Consequences

- Generated projects contain only what was chosen; a core-only project has no SQL, no NATS and a fraction of the dependencies.
- Contributors must put module-specific lines inside module blocks. The generator refuses unbalanced or misplaced markers, and the CI matrix catches a block that was forgotten (the smaller projects fail to build or verify).
- Four smoke combinations make CI slower; they run in parallel jobs if that becomes a problem.
- Reversal: drop the module markers; the template remains a working full-stack project.
